# Obsidian paper worker deployment

The React research site stays on GitHub Pages. The new Node 24 worker is separate from the browser: closing the website does not stop a deployed worker. The worker only knows `https://paper-api.alpaca.markets` and `https://data.alpaca.markets`. There is no live trading mode or configurable live endpoint.

## Easiest managed option: scheduled GitHub Actions

The workflow **Obsidian paper worker** is committed in `.github/workflows/paper.yml`. It runs at minutes 07, 22, 37, 52 during 13:00–22:59 UTC, Monday–Friday. The broker clock handles US holidays, daylight saving time, early closes and closed sessions. This is **scheduled unattended operation**, not a 24/7 resident process. GitHub can delay/drop scheduled jobs and disable inactive repository schedules; protection orders cannot run between jobs. The cron window covers US regular sessions in both summer and winter; no pre-/post-market submissions. The final snapshot is not an SLA or proof of continuous uptime.

Only these external actions are required if the account is not connected:

1. Create/use an Alpaca **paper** account. Use an empty dedicated paper account with no existing positions or pending orders, ideally reset to $10,000 before starting. No funded real account or paid market-data subscription is required by this code. Provider eligibility and availability depend on your account/region. Never reset an actively monitored account without resetting its corresponding risk state while the worker is stopped.
2. In this repository's **Settings → Secrets and variables → Actions**, add two **repository secrets**: `APCA_API_KEY_ID` and `APCA_API_SECRET_KEY`, using the **paper** keys. Never put values in chat, source files, Actions variables, URLs, screenshots, browser code, or the cloud configuration draft. Cloud-environment secrets are separate and do not automatically populate GitHub repository secrets.
3. Enable Actions. In **Settings → Pages**, select **GitHub Actions** as the deployment source if not already enabled. Run **Obsidian paper worker** once from Actions to check the connection. After that the schedule runs without trade-by-trade approval. Successful source pushes alone do not prove a worker or website is active.

The job restores `paper-state/state.json`, reconciles broker state, runs one cycle, commits sanitized observations/risk state to the separate `paper-state` branch, builds the dashboard, and deploys its snapshot to Pages. With `PAPER_REMOTE_STATE=true` in the hosted workflow, the monitoring baseline, risk peak and each order intent are committed to Git **before** any new POST. A failed remote journal stops submission; a killed runner does not silently discard a recorded intent. A broker error is persisted and visibly reported; the workflow may still succeed in publishing that **error** snapshot. It must not be interpreted as successful trading. Failure to persist state stops later steps. No fabricated orders/fills are substituted. The state branch contains paper positions, fills, balance history, logs, and a hashed account identity; raw account IDs and credentials are excluded. If this is a public repository, those **paper financial observations are public**. The dashboard is also public when Pages is public.

The state branch uses an ordinary non-force Git push and workflow concurrency prevents overlapping scheduled/manual cycles. The Pages deployment jobs share a concurrency group. Both the normal website pipeline and the worker preserve the latest automation snapshot. `GITHUB_TOKEN` only needs repository contents write for the cycle and Pages/id-token permissions for deployment; no personal GitHub token is required inside the workflow. Branch rules must permit the workflow to write `paper-state`. A missing source branch, Git permission, state parse error, missing credentials or HTTP error does not authorize a reset or blind retry.

GitHub Actions is free for public repositories under applicable GitHub terms. Private repositories have quotas, Pages plan restrictions and possible charges if billing is enabled externally. This task creates no subscription and enables no paid service. This schedule uses two short jobs per cycle; monitor repository usage and disable the schedule before exceeding your own account's included quota. Hosted runners are disposable: risk state survives in Git, not in a runner filesystem. GitHub Pages itself cannot execute the worker.

## True resident worker: container on an existing host

`Dockerfile` and `compose.yaml` build the tested app, run as a non-root user, preserve state in a named volume, expose a read-only dashboard/API on port 8080, and restart the process after normal container/host restarts. Use one worker for each dedicated paper account. **Disable the Actions schedule before using the resident container.** Do not run two deployment modes against the same account. A resident host, uptime, firewall and TLS/domain connection must already be available or supplied; no free VPS or paid hosting has been created by this task.

On that host, securely inject the same two paper environment variables, then deploy with `docker compose up -d --build`. Compose may load them from a local `.env` that is excluded from Git and Docker context. Do not place them in the compose file. State is in the `paper-state` volume; back it up encrypted/access-controlled. The listener binds to loopback on the host; expose only through an existing HTTPS reverse proxy. Never expose container/Docker administration sockets. This option serves `/` and `/automation/status.json` from one application origin, without CORS credentials or a browser API key. `/healthz` returns 503 for missing credentials/worker errors; a closed market or explicit pause is healthy but does not mean orders are being submitted. The dashboard refreshes every minute.

The in-process worker cycles every 60 seconds, uses bounded GET retries and 15-second timeouts, and shuts down gracefully. The state lock prevents overlapping processes sharing a volume. After an abrupt crash, an exclusive `.lock` file may remain: fail-closed recovery is intentional. Establish that the prior process is dead, preserve a backup of the state volume, then remove only the stale lock before restarting. Never delete the state JSON to clear a lock.

## Risk and order behavior

- Rule-based 20/50 daily SMA trend, not an AI profit predictor. BUY targets an entry when SMA 20 > SMA 50, SELL targets exit when below, HOLD on equality/warmup. Only bars through the **previous completed exchange session** can affect a new order. The last bar must match the broker calendar; otherwise hold. Alpaca IEX is one exchange, not consolidated SIP/NBBO market-data coverage. Latest quote must be no older than 120 seconds, not more than five seconds in the future, uncrossed, and no wider than 50 bp. Data gaps/entitlement errors stop submissions rather than selecting a paid feed or using archived quotes.
- Fixed unleveraged allowlist SPY/AGG/AAPL. Capital budget is `min(account equity, $10,000)`. Each new position is at most 10% of that budget, aggregate exposure at most 30%, and at least 5% of budget is reserved in cash. Sizing uses **cash**, never buying power. Entries use whole units. Exits round down to six decimals and never exceed holdings; sub-$1 dust notional may remain. Negative cash, short/unsupported positions, manual orders, or a different account identity stop automation. The account can report margin buying power, but the worker neither uses it nor requests leverage. Use a dedicated account to avoid concurrent manual changes.
- 8% per-position loss check; trim positions more than 10% above the position-value cap; 3% account daily loss blocks entries and attempts exits; 10% observed account drawdown permanently latches entry halt. Risk is sampled, not continuously guaranteed. Loss stops use whole-account equity/last-equity; deposits, withdrawals and account resets invalidate simple performance interpretations. A large idle cash balance makes account-percentage stops less sensitive than invested-position stops.
- Day limit orders only, no extended hours. Limits are 10 bp adverse to a fresh ask/bid, rounded to price ticks. This bounds order price, but **does not guarantee a fill or a stop-loss exit**. No new buys in the last 15 minutes before the broker's next close. Pending orders block additional exposure. Bot orders older than five minutes are cancelled at the next cycle, and acknowledged cancellation must reconcile before another order. The scheduled mode's TTL is consequently only checked at scheduled runs, not precisely five minutes later.
- One deterministic buy ID and one sell ID per symbol per exchange date. After an unknown POST acknowledgement, look up the same client ID; never blindly resend. Submission intent is durably recorded before POST; even if no acknowledgement can be found after a timeout or crash, that ID is not resubmitted that session. Existing IDs, including rejected/cancelled/partial orders, are also not resubmitted. A crash between recording intent and submission can therefore skip an order for the day. An attempted sell prevents same-day re-entry. Partially filled/cancelled exits can leave exposure until a later session. Broker rejection is recorded, not overridden; this includes account/PDT protection checks. A successful POST is an acknowledgement, not a fill. FILL activities supply actual observed quantities/prices on later cycles.

## Stop and recovery

Set repository **variable** `PAPER_KILL_SWITCH=true`, then run the paper workflow. It cancels managed open orders and pauses new orders; existing positions remain exposed. To stop scheduling entirely, disable the paper workflow in Actions (this alone does not cancel outstanding orders). For the resident mode, inject `PAPER_KILL_SWITCH=true` and restart it so a cycle can reconcile/cancel; then stop the container if desired. Keep credentials secure and never substitute live keys.

A max-drawdown latch is intentionally not auto-reset. While workers are stopped, reconcile positions/open orders with the provider, back up the state, and have an operator explicitly review/reset the `halted` flag and any intended new risk baseline. A corrupt/unreadable state is never replaced with an empty file automatically. Broker/account reset or credential rotation to a new account requires an empty dedicated paper account and an explicit new monitoring state; raw account identifiers are not logged. Retain the old state for audit. Closed-sell-fill win rate is unavailable if corporate actions or missing cost basis make the fill ledger unreconcilable; never manufacture a replacement rate.

## Performance interpretation and current limitations

The dashboard distinguishes real broker **paper** observations from browser historical replay and historical automation backtests. Account P&L is equity minus first observed equity and is not cash-flow-adjusted; fees follow the broker's balance treatment. A separate weighted-cost ledger models 10 bp per fill for realized P&L and win rate without deducting those costs again from the account balance. Win rate counts closed **sell fills**, not completed round trips. Actual slippage is not estimated without a fill-time reference quote. Exported broker fills are source observations, not predictions.

`npm run backtest:report` runs the same order-sizing/stop planner against the genuine bundled adjusted archive and writes `public/automation/backtest.json`. It uses prior-close signals, idealized next-open execution with 10 bp adverse slippage plus tick rounding, 10 bp per-side fees, and final-close liquidation. Production polling may trade later and may not fill at all. The initial benchmark allocates 10% to each asset and leaves cash idle; its holdings can grow beyond those initial weights, while the strategy maintains a fixed capital cap. Thus their risk/exposure paths differ. Both use the same execution costs. Provider adjustment revisions, archive age, survivor selection, liquidity, corporate actions, cash interest and taxes limit conclusions. These are simulations, not live or broker performance.

The website must not label missing/stale status as running. `lastSuccess` records a completed cycle, not proof of uptime or trading; last known balances remain timestamped during errors. No model or strategy guarantees profits.
